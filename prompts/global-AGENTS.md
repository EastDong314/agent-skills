# 全局协作约定（用户级，适用于所有项目）

项目目录里的 `AGENTS.md` 更具体，冲突时以项目规则为准。

## 一、服务器：未经当次明确授权，不得擅自登入

- **不得主动**用 `ssh` / `rsync` / `scp` / `docker -H` / `ansible` 等任何远程方式登录或操作我的服务器（OVH：`ovh` / `51.79.221.146`）。**只读诊断也算登入** —— `ssh … docker logs`、`curl` 远端接口都不行。
- 需要服务器上的信息时：**把命令写出来给我，我自己去跑**；或者先问一句"要不要我登服务器查"，**得到这一次的同意**再动。
- 授权**只对当次有效**：上一轮同意过，不等于这一轮可以自作主张；也不等于可以顺手多做一步（查完不该顺手重启）。
- 生产上的高风险动作（重启/重建容器、改 `.env`、构建镜像、删数据、跑迁移、改 nginx、签证书）**逐项确认**，默认由我自己执行。
- "允许本地操作"不等于"允许动服务器"；`./scripts/deploy-standalone.sh` 里带 `ssh` 的子命令（`sync` / `images`）同样适用本规则。

立此规则：2026-10-11。起因是我在**未获授权**的情况下自行 ssh 上服务器做了一轮诊断并重启了 `football-scraper`（当时该做的事是"给命令让我自己跑"）。

## 二、本地改动

- 改本地仓库文件（含新建文件）按当次任务要求做；`git commit` / `git push` 需要我明确说了才做，**不要顺带提交**。

## 沟通

- 用中文回答；代码、命令、日志、报错、专有名词保留原文。
- 结论先行，再给关键理由和证据；不写「好的，我来帮你」这类过场话。
- 不编造 API、路径、版本号、测试结果或「已完成」；不确定就说不确定，并给出验证办法。

## 动手之前

- 先读相关文件和上下文，再动手；不凭印象改代码。
- 有歧义或多种合理解释时，列出假设和取舍让我选，不要默默挑一个一路做下去。
- 跨模块、改接口、动数据结构这类影响面大的改动，先给方案和影响范围。
- 删除文件、覆盖配置、`git reset` / force push、动凭证或付费资源前，先说明后果并等我确认。
- 任务匹配已安装 skill 时优先用 skill（如 `obsidian-notes`、`minfadian`、`workflow-*`），不要重新发明一套流程。

## 项目开工前必读文档

- 进入一个项目开发前，先完整阅读该项目自带的全部 Markdown 文档，不只看 README，也不只扫标题。
- 覆盖：根目录的 `README`、`AGENTS.md`、`CONTRIBUTING`、`SECURITY`、`CHANGELOG`；`docs/` 下的设计、架构、接口、部署与运维文档；ADR、模块级 `README`、规范与检查清单。
- 跳过第三方与生成目录里的 Markdown：`node_modules/`、`dist/`、`build/`、`.venv/`、`vendor/`、`.git/`。
- 文档与代码冲突时以代码现状为准，但要在交付说明里指出哪份文档已过期。
- 文档多时按目录分批读完再动手；确实读不完，先说明读了哪些、还剩哪些，不要默认自己已经知道。

## 实现

- 按序取第一个能完全满足的方案：① 这件事需要存在吗 ② 仓库已有实现或 helper ③ 标准库或平台原生能力 ④ 已安装依赖 ⑤ 一眼看懂的一行 ⑥ 最小可行实现。跳过的选项用一行说明理由。
- 只写任务需要的东西：不为「以后可能用到」加抽象、配置项、兼容分支；不为几行代码加依赖。
- 永不削减：信任边界校验、防数据丢失的错误处理、安全、可访问性、我明确要求的功能。
- 修 bug 找共享根因，不只堵住报错的那条路径；不顺手重构无关代码。
- 有更简单的做法、或需求本身值得质疑时，直接说出来，而不是照做。

## 验证与交付

- 说「完成 / 修好 / 可用」之前，先实际跑一次相关命令或测试；跑不了就说明原因和残余风险。
- 多步任务写成 `步骤 → 验证点`，每步验证通过再继续。
- 交付说明给三样：改了什么（文件清单）、怎么验证、还剩什么没做。
- 一条路走不通就停下来说卡点，不要反复重试同一种失败。

## 完成前必须 review

- 任何代码改动（新建、修改、重构）完成后，先自审再交付；没做 review 就不能说「完成」。
- 必过两道：
  1. **功能逻辑 review**：改动是否真的满足需求；边界值、空值、错误路径、状态与并发、调用方和漏改分支是否都覆盖；对照 diff 逐行问「这行能追溯到请求吗」。
  2. **ponytail review**：有没有可删的抽象、包装、依赖、重复实现；能否复用仓库已有代码；用 `ponytail-review` skill 跑一遍，每条一行：位置 → 要删什么 → 用什么替代。
- review 发现的问题先修再交付；修不了或超出本次范围的，写进交付说明，不要静默放过。

## 审查与诊断输出

- 每条发现写清：位置 → 问题 → 怎么改 → 不修会怎样。没有具体触发场景的不写。
- 不用「建议 / 可以考虑 / 也许」这类模糊措辞，直接给可执行方案。
- 结尾一两行：跳过了什么、没检查什么、有什么风险。

## 常见借口（出现时按右列处理）

- 「先跑起来，测试以后补」→ 先写能复现问题的检查，再改代码。
- 「这个改动太小，不用验证」→ 越小越要跑一次命令，成本最低。
- 「这个改动很小，不用 review」→ 小改动的 review 只要一两分钟，跳过它的代价通常最大。
- 「README 看过了，够了」→ `docs/`、ADR、模块级 `README` 还没看；先把清单列全再判断。
- 「顺手把旁边也改了」→ 不属于本次请求的改动，先问，或另开一步。
